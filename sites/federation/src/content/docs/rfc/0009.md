## Summary

The AT Protocol Lexicon record schemas in `lexicons/com/aegisfederation/governance/` predate the GFN-1 v1.0 specification and do not match the normative event schemas defined in [`/spec/schema/`](/spec/schema/). This RFC will define the realignment: which model wins, how breaking changes are versioned, and the migration path for the reference feed generator and PDS.

This is a **high-priority** RFC. As long as the lexicons and the spec disagree, implementations cannot interoperate from both sources.

## Motivation

The current state of the federation has two normative-feeling sources for the same information that disagree on form and substance:

| Topic | Lexicons (`lexicons/com/aegisfederation/governance/*.json`) | Spec (`/spec/schema/`) |
|---|---|---|
| **Event-type modelling** | Single `signal` record type with a `type` discriminator (`"circumvention" \| "risk_alert" \| "policy_violation" \| "anomaly" \| "advisory"`) | Distinct event types per kind: `governance.circumvention_report.v1`, `governance.risk_signal.v1`, `governance.policy_update.v1`, `governance.attestation.v1`, `governance.incident_notice.v1` |
| **Field naming** | camelCase (`entityDid`, `affectedCapabilities`, `validFrom`) | snake_case (`publisher_did`, `affected_capabilities`, `valid_from`) |
| **Field set** | Lighter, legacy field set (`affectedCapabilities`, `mitigations`, `references`, `severity`) | Richer, normative field set per event type — for example `governance.circumvention_report.v1` requires `technique_id`, `category`, `severity`, `description`, `observed_at`; SHOULD include `attack_pattern`, `indicators`, `affected_models`, `affected_controls`, `mitigation_recommendations`, `confidence`, `exploit_reproducibility` |
| **Visibility model** | Not represented | `visibility` field with values `public \| restricted \| private` |

The README and CLAUDE.md currently call this drift out and declare the spec authoritative for new implementations. This RFC will turn that into a concrete realignment plan.

## Anticipated Topics

- **Decision: which model wins.** The expected answer is "lexicons are realigned to match the GFN-1 spec" — distinct event types per kind, snake_case fields, the spec's full field set. Alternative answers (and reasons to reject them) will be documented.
- **AT Protocol convention compatibility.** Bluesky/atproto idiomatically uses camelCase. Diverging may surprise atproto implementers; the RFC will document the rationale (cross-spec consistency with the snake_case convention used in GFN-1 documentation, RFC-0004, and most cybersecurity-domain peers like STIX).
- **Breaking-change handling.** The current lexicons may have no external consumers yet, but the RFC will specify how the change is versioned (likely retiring `com.aegisfederation.governance.signal` in favour of separate records `com.aegisfederation.governance.circumventionReport`, `com.aegisfederation.governance.riskSignal`, etc., or moving entirely to a `governance.<event>.v1` flat namespace).
- **Lexicon namespace decision.** Whether to keep `com.aegisfederation.governance.*` (atproto-idiomatic, reverse-DNS) or move to flat `governance.<event>.v1` lexicon IDs that match the spec's event type names exactly.
- **Reference implementation impact.** Updates required to `feed-generator/` (firehose filtering by record type) and `pds/` (record validation).
- **Conformance impact.** Whether existing language in [`/spec/conformance/`](/spec/conformance/) needs adjustment to reference the new lexicon record types directly.
- **Migration window.** Whether the legacy lexicons remain readable for a deprecation period (likely yes, with a clear deprecation notice and target removal date).

---

## Acceptance Criteria

This RFC is considered **Final** when:

1. The decision on the canonical lexicon model is documented and accepted.
2. New lexicon JSON files conforming to that decision are merged into `lexicons/`.
3. The reference `feed-generator/` is updated to filter and validate against the new lexicons.
4. Test vectors for each event type are added to `test-vectors/` and exercised in CI.
5. The `[/spec/conformance/](/spec/conformance/)` document is reviewed and amended if needed.
6. README and CLAUDE.md "Known migration items" entries about lexicon drift are removed.
