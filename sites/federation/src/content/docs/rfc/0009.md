## Summary

The AT Protocol Lexicon record schemas in `lexicons/com/aegisfederation/governance/` predated the GFN-1 v1.0 specification and did not match the normative event schemas defined in [`/spec/schema/`](/spec/schema/). This RFC realigns them: the lexicons now match the spec's event-type registry, field naming, and field set exactly, with one deliberate exception for a real cross-spec incompatibility (see Decision 5).

This was a **high-priority** RFC. As long as the lexicons and the spec disagreed, implementations could not interoperate from both sources.

---

## Motivation

Before this RFC, the federation had two normative-feeling sources for the same information that disagreed on form and substance:

| Topic | Lexicons (legacy) | Spec (`/spec/schema/`) |
|---|---|---|
| **Event-type modelling** | Single `signal` record type with a `type` discriminator (`"circumvention" \| "risk_alert" \| "policy_violation" \| "anomaly" \| "advisory"`) | Distinct event types per kind: `governance.circumvention_report.v1`, `governance.risk_signal.v1`, `governance.policy_update.v1`, `governance.attestation.v1`, `governance.incident_notice.v1` |
| **Field naming** | camelCase (`entityDid`, `affectedCapabilities`, `validFrom`) | snake_case (`publisher_did`, `affected_capabilities`, `valid_from`) |
| **Field set** | Lighter, legacy field set | Richer, normative field set per event type |
| **Visibility model** | Not represented | `visibility` field with values `public \| restricted \| private` |

---

## Design Decisions

**1. Which model wins: the lexicons realign to the spec.** Distinct event types per kind, snake_case fields, the spec's full field set. No alternative was seriously considered -- the spec is the normative artifact external implementers read; the lexicons are the AT Protocol-specific encoding of it, not an independent source of truth.

**2. Field naming diverges from AT Protocol convention, deliberately.** Bluesky/atproto idiomatically uses camelCase. The lexicons use the spec's snake_case field names exactly (`event_id`, `publisher_did`, `technique_id`, ...) instead. Rationale: cross-spec consistency with the snake_case convention used throughout GFN-1 documentation, RFC-0004, and cybersecurity-domain peers like STIX outweighs the cost of surprising atproto-only implementers, since GFN-1's primary audience already reads it as a security-domain spec first and an atproto application second.

**3. Breaking change, no deprecation window.** The legacy records (`signal`, `capability`, `policy`, `incident`, and the old `attestation` shape) are retired outright, not kept readable alongside the new ones. A deprecation window protects existing consumers from a breaking change; there are none -- `feed-generator/src/index.ts`'s `getFeedSkeleton` has never returned anything but an empty stub, and no PDS instance has ever been deployed (tracked separately in #2). Nothing live depends on the legacy shape.

**4. Lexicon namespace: kept, but decoupled from the spec's `event_type` string.** `com.aegisfederation.governance.*` stays as the atproto NSID (collection identity), rather than moving to a flat `governance.<event>.v1` lexicon ID. The spec's exact `event_type` string (e.g. `governance.circumvention_report.v1`) is carried as a required field *value* inside each record instead of as the lexicon's own identifier. This gets both: atproto-idiomatic reverse-DNS collection NSIDs (`com.aegisfederation.governance.circumventionReport`, etc.) for AT Protocol tooling, and the spec's exact registered string for cross-system matching, with no conflict between the two naming schemes.

**5. One real spec incompatibility: no floating-point type.** The spec defines several `confidence` fields as `number 0..1`. AT Protocol Lexicon v1 has no floating-point primitive -- only `integer`, `string`, `boolean`, `array`, `unknown`, `bytes`, `cid-link`, `ref`/`union`, `blob`. Confirmed by reading `@atproto/lexicon`'s compiled type definitions directly, not assumed. Resolution: `confidence` is represented in the lexicons as an integer percentage (0-100), documented inline in each schema's field description. Implementations translate by dividing/multiplying by 100 at the lexicon boundary; the canonical GFN-1 envelope concept remains the 0..1 float.

**6. `knownValues` vs. `enum`.** AT Protocol Lexicon distinguishes these: `knownValues` is advisory (unknown values pass, for forward-compatibility -- confirmed by testing against the library directly, not assumed from its name), `enum` is a hard closed set. Fields the spec marks `(string)` with illustrative "e.g." values (`category`, `risk_category`, `classification`, `incident_class`) use `knownValues`. Fields the spec marks `(string enum)` with an exhaustive pipe-separated list (`severity`, `trend`, `assurance_level`, `exploit_reproducibility`, and the envelope's `visibility`) use `enum`.

**7. `com.aegisfederation.governance.capability` is retired with no direct replacement record.** GFN-1 does not register a capability-declaration event type. Its concept (capability/control declarations) is now expressed through `governance.attestation.v1`'s `controls_implemented` and `compliance_profiles` fields rather than as a standalone record type.

**8. Array-of-object and inline-object fields require a `ref`, not an inline `type: object`.** Lexicon has no inline object type for array items or object properties -- confirmed while fixing [#3](https://github.com/aegis-initiative/aegis-federation/issues/3), which hit this exact issue in the legacy lexicons. Every structured sub-object in the new lexicons (the envelope/payload split itself) uses `{"type": "ref", "ref": "#payload"}`.

## What changed

- **Retired:** `signal.json`, `capability.json`, `policy.json`, `incident.json`, and the old `attestation.json` shape.
- **Added:** `circumventionReport.json`, `riskSignal.json`, `policyUpdate.json`, `incidentNotice.json`, and a rewritten `attestation.json` -- one lexicon per GFN-1 registered `event_type`, each with an envelope (matching [Schema §2](/spec/schema/#2-aegis-event-envelope-required)) wrapping a typed `payload` ref.
- **Added:** `test-vectors/` with valid and invalid record examples for all 5 event types, validated in CI against the real `@atproto/lexicon` schema (`assertValidRecord`), not a no-op.

## Acceptance Criteria

1. ✅ The decision on the canonical lexicon model is documented (Design Decisions above).
2. ✅ New lexicon JSON files conforming to that decision are merged into `lexicons/`.
3. ⏸️ **Deferred to [#1](https://github.com/aegis-initiative/aegis-federation/issues/1).** `feed-generator/`'s firehose connection and filtering logic don't exist yet -- there's nothing to "update" to the new lexicons, since the filter predicate itself has never been implemented. The `getFeedSkeleton` TODO comment now names the 5 current event types so #1 doesn't start from a stale reference.
4. ✅ Test vectors for each event type added to `test-vectors/` and exercised in CI.
5. ✅ [`/spec/conformance/`](/spec/conformance/) reviewed -- no amendment needed. It already references the spec's envelope/event-type terminology directly rather than the legacy lexicon shape, and its "Reference test vectors" section already pointed at `test-vectors/`, which this RFC populates for the first time.
6. ✅ README.md and CLAUDE.md's lexicon-drift "Known migration items" entries removed. (The PDS-deployment entry is unrelated to this RFC and stays, tracked in #2.)
